# Wand source

- `app` registers `Wand` through the capability traits in `model`. Keep source-specific behavior in this crate.
- Never bundle or commit third-party binaries. Check hashes and publisher signatures before loading them (`PUBLISHERS`: WeMod LLC, and its earlier name Daring Development Inc. on older trainers); keep verified images locked until the run ends. The service and plugin are those of the trainer's architecture (`binaries`), as Wand picks them.
- Keep credentials inside the session code and protect them with user-scoped DPAPI. Never log tokens, auth codes, headers or response bodies.
- Catalog `platforms.uwp.containers` (by package family, any case) is `Game::package_apps`: Halo MCC's start without its anti-cheat. `platforms.uwp.ignore` is not read: it filters the packages Wand scans, and no catalog id matches it.
- Treat remote ids, paths and links (`purchaseUris`, reaching `launchers::store_link` only) as untrusted. Preserve listener scope and limits. Read the user's installation and settings without modifying them.
- `launch.proxy` (`proxy.rs`) is the one write into a game's folder, for a store's start only: Wand's `GameLauncher.exe` from its install, signature-checked, stands in for the launcher, which waits beside it as `.wand-backup`, with `.wand-config` naming what to start. Its paths are plain relative files, and the folder written is the game's after links resolve. A leftover it cannot account for is refused, never overwritten; the stand-in's own `.wand` and `.wand-config` are replaced. The stand-in puts the launcher back itself once the game starts; dropping the mount does too, off the dropping thread, and a retry's mount waits for that restore. The stand-in runs on its own and is not held locked: it moves itself aside.
- The process looked for is `target.image`, else the proxy's `gameExe`: never the anti-cheat's launcher. `target.reducer` is Wand's number (1 oldest, 2 newest, anything else the most memory), `target.cliArgs` the command-line filter, `target.timeout` the wait after a start (ms), `launch.cliArgs` the start's arguments (empty is none). `blueprint.notes` reach the UI as the trainer's notes, in the answer's language.
- The game version a run sends is the install's build (`attach`'s, the catalog `versionPath`'s stamp the scan read), 0 when unknown: Wand's `gameVersion ?? 0`, never the running exe's. Before the service goes in, a last session's teardown in that process is waited for as Wand does (`Local\TophatService_TeardownComplete_<pid>`, 30 s; late only warns).
- `activate.flags` (`trainer::Activate`) as Wand's Tophat path reads them (`attach`): every trainer waits up to 10 s for the game to take input (`agent::idle`); 1 suspends the game until the trainer is ready, and only with 2 is it resumed then (any failure or drop after a suspend resumes it, once); a suspend we are denied (an elevated game) warns and goes on. 16 starts Wand's `TrainerHost_<trainer arch>.exe <gamePid> 1000` (`trainer_host.rs`, an `agent::Program`, no window), the service goes into it and the teardown wait is on its pid, the trainer is still told the game's pid; the `Live` session holds it and ends it 2 s after the session (10 s once the game is gone). 4 and 8 are Wand's classic loader only: such a trainer's attach failure that is `Internal`, `LoadFailed` or `TrainerFailed` says so. The wait for the service to dial in (45 s) ends as soon as the game or the host exits (`agent::exit`), as Wand's: the game's exit is `GameExited`, the host's alone unmarked. A service load not marked by `agent` is `LoadFailed`, a trainer's start that fails `TrainerFailed`. A service that never dials in asks for a newer Wand.
- A trainer places the player (`Trainer::location`) by its blueprint's bit 8 or a map of its title with the catalog map flag 2, and teleports by bit 4 or a title map's `supportsTeleport`, else its flag 4 (`catalog::Marks`): Wand's maps read only the map flags. The position is the legacy `wm_coord_*` exchange; an axis never sent is NaN.
- A map's `gameCoordsMap` names the game axes along the plane's x and y, which must differ; up is the third, whatever its `z` names (Castor Woods names x twice). Pin `gameCoords` and reference points are in the game's own order, never remapped.
- A map's tiles: an xyz source, or a PMTiles archive's xyz `fallback` first. An archive without one counts only on the maps CDN (`archives::template`): its tiles are `wand:pmtiles/<uuid>/{z}/{x}/{y}`, which `Downloads` answers by rebuilding the CDN address from the uuid alone, never from map data. `map::Archives` (the provider's) keeps headers and directories, bounded; a changed ETag drops the archive's. A tile it lacks is `NotFound`, a URL not of this form or an archive it cannot read `Refused`.
- Every request of ours to WeMod names itself `install::user_agent()` (`Wand/<newest install at start>`, read once): the bridge adds it to WebView2's, and `Wand::new` gives it to `fetch::name_as` for `wemod.com` (catalog, art, maps, trainers). On some networks WeMod's edge turns away other clients (a Turnstile on sign-in, a 404 on a trainer DLL).
- Never prefetch trainers. A trainer DLL is asked for bare first, as Wand's `https.get` asks, then named; a failed connection or a body of another hash is a failed ask too, and a failure names every ask. A trainer DLL the CDN cannot give (a 404 that depends on the user's network, an offline start) is taken from Wand's own download (`%APPDATA%\<brand>\App\trainers\Trainer_<id>_<hash10>.dll`, read only), only when it hashes to the one the API names, and copied into ours.
- API errors log method, path and HTTP status when available, never the query or response body. A `TypeError` triggers a credential-free `no-cors` probe of the origin; its result is not a CORS diagnosis.

## Overlay (`overlay/`, `Overlays`)
- Only for a game whose catalog `flags` has 256 (`catalog::Marks`, set by each catalog parse). Wand's `overlay_game_x64.dll` / `overlay_game.dll` from the install, by the process's architecture (`agent::x64`), signature-checked, `agent::map`ped once per process under one lock and kept locked until that process is gone. A failed load is not tried again (a timed-out one may still land); a declined UAC prompt (a game run as administrator) is not asked again for that process.
- The DLL dials a hidden window titled with its fixed name: one host thread per app, `Refused` while Wand's own host holds it. Every CONNECT is answered at once (ACK, or the goodbye while resting), also from a DLL `enter` has not recorded yet: an unanswered one stays connecting for good, even to a later host.
- A game's link lasts while that game runs: the DLL rebuilds its graphics on every disconnect (a game froze on it), so a closed canvas only closes its layers. The host starts resting (a failed `enter` must not hold Wand's title); resting renames its window first, then says goodbye to the other links (said while findable, the DLL dials again at once).
- Every message goes from the host thread, never inside the DLL's own send, and is built with serde: a malformed one kills the DLL's thread. Frames go only to a canvas of a process we mapped; they are sent again 250 ms after `graphics-window-info` (the DLL drops them).
- The DLL's own hotkey is key 0: ours asks for the block. Keys reach an interactive layer only once its window is clicked.
- `state.rs` decides (no Win32 but the window memory; its tests hold the block, the last words, `Ready`, the cursor, another GPU, resting); `host.rs` sends.
